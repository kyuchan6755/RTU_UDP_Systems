# Git 초보 매뉴얼 — Claude Code 사용자 관점

핸드폰/PC에서 Claude Code로 개발하는 사람을 위한 git 입문서. 어려운 용어는 일상 비유로 풀고, **실제로 무엇이 일어나는지**에 집중합니다.

---

## 0. 이 매뉴얼이 다루는 것

- git이 **왜 필요한지** — 안 쓰면 무엇이 불편한지
- 핵심 **8개 용어** — 외울 게 이게 다입니다
- Claude Code 모바일/웹에서의 **일상 작업 흐름** — 진짜 매일 쓰는 것만
- **충돌**이 나면 어떻게 — 무서워하지 않게
- **자주 하는 실수**와 회피법

다루지 않는 것: rebase, cherry-pick, stash, reflog (필요할 때 따로 찾아보면 됨).

## 1. 한 줄로 git이란

> "파일을 수정한 이력을 **언제 / 누가 / 무엇을** 바꿨는지 기록하고, 과거 어느 시점으로든 돌아갈 수 있게 해주는 도구."

비유: 게임 세이브 + 그 세이브에 메모를 남길 수 있는 시스템.

---

## 2. 핵심 8개 용어 (요리 레시피 노트 비유)

큰 그림:

```
[내 컴퓨터에 있는 레시피 노트]   ←→   [도서관에 있는 같은 노트]
        (로컬)                        (GitHub - 인터넷)
```

### 2-1. Repository (저장소) — "노트 한 권"
프로젝트 파일들 + 그동안의 모든 수정 이력이 한 묶음으로 들어있는 곳.

### 2-2. Commit (커밋) — "이 순간을 저장 + 메모"
새 페이지를 적고 "오늘 김치찌개 레시피 추가함"이라고 메모 남기는 것. 나중에 이 책갈피로 정확히 돌아올 수 있음.

### 2-3. Branch (브랜치) — "원본 안 망치는 실험본"
원본 페이지는 그대로 두고, 빈 페이지에 매운맛 버전을 따로 적는 것. 망쳐도 원본은 안전.

### 2-4. Push — "내 노트 → 도서관에 옮겨 적기"
내 컴퓨터에만 있는 커밋들을 GitHub에 올림.

### 2-5. Pull — "도서관 → 내 노트로 받아오기"
push의 반대. 다른 사람이 GitHub에 올린 변경을 내 컴퓨터로 가져옴.

### 2-6. Clone — "도서관 노트를 처음부터 통째 복사"
저장소를 처음 한 번 받을 때 쓰는 명령. 그 다음부턴 pull로 업데이트.

### 2-7. PR (Pull Request) — "내 실험본 추가해줘 요청"
"내 브랜치(실험본)의 내용을 main(원본)에 합쳐도 될까요?" 공식 결재 요청. 검토와 토론을 거쳐 승인되면 합쳐짐.

### 2-8. Merge (병합) — "승인! 합치기"
PR이 승인되어 실제로 두 갈래 페이지를 하나로 합치는 것. 같은 줄을 다르게 수정했으면 **충돌(conflict)**.

## 3. 가장 헷갈리는 4가지

### Q: commit과 push 차이?
- commit = **내 노트에만** 저장 + 책갈피
- push = 그 책갈피들을 **도서관(GitHub)에도** 보내기
- commit만 하고 push 안 하면 → 다른 데서 못 봄. 컨테이너 끝나면 사라짐.

### Q: branch는 왜 필요한가?
- main에 직접 작업 → 실수하면 모두가 보는 원본 망가짐
- branch에서 작업 → 망쳐도 그 브랜치만 버리면 됨
- 그래서 Claude Code도 매 세션마다 자동으로 새 브랜치 만듦

### Q: PR과 merge 차이?
- PR = "합쳐주세요" **요청** (검토 단계)
- merge = 요청 승인 후 **실제로 합치기** (실행 단계)
- 순서: PR → 검토/수정 → 승인 → merge

### Q: 충돌(conflict)이 뭔가?
- 두 브랜치가 **같은 파일의 같은 줄**을 서로 다르게 수정했을 때
- git이 "둘 중 뭐를 살릴지 사람이 결정해" 라며 멈춤
- 무서운 게 아니라 **사람의 결정이 필요한 정상 상황**

## 4. Claude Code 모바일/웹에서의 일상 흐름

```
[새 세션 시작]
   ↓
시스템이 자동으로:
- 새 컨테이너 생성
- GitHub 저장소 clone (자동)
- 새 브랜치 자동 생성 (claude/<요약>-<랜덤5>)
   ↓
[사용자: 명령 입력]
"○○ 만들어줘"
   ↓
Claude가 컨테이너에서 파일 작성
   ↓
[필요 시] git commit + git push 수행
   ↓
시스템이 자동으로 draft PR 생성
   ↓
[사용자가 검토 후 머지 결정]
   ↓
PR merge → main에 변경 반영
```

**핵심**: 브랜치 생성, push 후 PR 자동 생성 등은 **시스템이 알아서 해줌**. 사용자는 코드 변경과 검토 결정에만 집중하면 됨.

## 5. 자주 쓰는 명령 12개 (분류별)

### 상태 보기 (제일 자주)
```bash
git status                  # 어떤 파일이 바뀌었나?
git status --short          # 짧은 버전
git diff                    # 정확히 뭐가 바뀌었나? (커밋 전)
git log --oneline -10       # 최근 10개 커밋
git log --oneline --graph   # 그래프로 보기 (브랜치 시각화)
git branch --show-current   # 지금 어느 브랜치?
```

### 변경 → 커밋
```bash
git add <파일>               # 스테이지에 올림
git add -A                  # 변경 전부 스테이지
git commit -m "메시지"       # 커밋 (커밋 메시지 필수)
```

### 브랜치
```bash
git checkout -b <이름>       # 새 브랜치 만들고 이동
git checkout <이름>          # 기존 브랜치로 이동
git branch                  # 로컬 브랜치 목록 (* 가 현재 위치)
git branch -d <이름>         # 머지된 브랜치 삭제 (안전)
```

### 원격 동기화
```bash
git push -u origin <브랜치>  # 첫 push (-u로 추적 등록)
git push                    # 이후 push는 그냥
git pull                    # 원격 변경 받기
```

### 머지
```bash
git merge <브랜치>           # 현재 브랜치로 다른 브랜치 합치기
git merge --abort           # 머지 도중 취소
```

## 6. 충돌이 나면 — 실전 절차 5단계

### 1단계: 충돌 메시지 확인
```
$ git merge feature/X
Auto-merging some_file.txt
CONFLICT (content): Merge conflict in some_file.txt
Automatic merge failed; fix conflicts and then commit the result.
```

### 2단계: 어떤 파일?
```bash
$ git status
both modified:   some_file.txt
```

### 3단계: 파일을 열어보면 마커가 있음
```
<<<<<<< HEAD
현재 브랜치 내용
=======
합치려는 브랜치 내용
>>>>>>> feature/X
```

### 4단계: 마커들 다 지우고 원하는 최종 내용으로 편집
4가지 선택:
- 현재 거(HEAD)만 남기기
- 합치려는 거(feature/X)만 남기기
- 둘 다 합치기
- 완전 새 내용으로 다시 쓰기

### 5단계: 해결 완료를 git에게 알리기
```bash
git add some_file.txt    # 사람이 해결했다고 표시
git commit               # 머지 커밋 만들기 (메시지 자동 제안됨)
```

**중간에 포기하고 싶으면**: `git merge --abort`

## 7. 자주 하는 실수 TOP 5

### 1. main에서 직접 작업하기
- 모두가 보는 원본을 갑자기 바꾸면 사고
- **해결**: 항상 `git checkout -b feature/something` 으로 브랜치 만들고 작업
- Claude Code는 이걸 자동으로 해줌

### 2. 커밋만 하고 push 안 함
- 컴퓨터에만 있는 변경은 다른 데서 안 보임
- 컨테이너 종료 = 변경 사라짐
- **해결**: 작업 끝나면 `git push` 습관화

### 3. 커밋 메시지를 "수정함", "asdf" 같이 의미 없이
- 3개월 뒤 자기도 뭐 했는지 모름
- **해결**: "왜" 바꿨는지 한 문장으로
  - 안 좋음: `fix`, `update`, `완료`
  - 좋음: `fix: 로그인 시 비밀번호 공백 처리 누락`

### 4. `git push -f` (강제 push) 남용
- 다른 사람이 같은 브랜치 작업 중인데 강제 push → 그 사람 작업 날아감
- **해결**: 본인만 쓰는 브랜치 외에는 `-f` 쓰지 말 것
- 정 필요하면 `--force-with-lease` (안전한 버전)

### 5. `.env` / 비밀번호 / API 키를 커밋
- GitHub에 올라가면 인터넷에 노출됨 (지워도 이력에 남음)
- **해결**:
  - `.gitignore`에 `.env`, `*.key` 등록
  - 커밋 전 `git diff --cached` 로 한 번 확인
  - `/버전업` 같은 스킬은 자동으로 차단

## 9. Q&A

### Q: 세션 종료하면 작업이 사라지나?
- **컨테이너 로컬 파일**: 사라짐
- **GitHub에 push한 커밋**: 영구 보관
- **PR**: GitHub에 살아있음
- → push가 곧 보험. 작업 끝나면 항상 push.

### Q: 브랜치 이름은 어떻게 짓나?
관례: `<type>/<설명>`
- `feature/login-page` — 새 기능
- `fix/payment-bug` — 버그 수정
- `docs/api-guide` — 문서
- `refactor/db-layer` — 리팩터링
- `claude/...` — Claude Code 자동 생성

### Q: 한국어 파일명/브랜치명 써도 되나?
- 됨. 단 콘솔에선 `\353\262...` 처럼 escape돼서 표시될 수 있음 (저장은 정상)
- GitHub 웹에선 한글로 잘 보임

### Q: PR을 draft로 만들면 뭐가 다른가?
- draft = "아직 머지하지 마, 더 작업할 거야" 표시
- 보통 머지 버튼이 비활성화됨
- 완료되면 "Ready for review"로 전환

### Q: 머지 후 브랜치는 어떻게 하나?
- 보통 삭제 (역할 끝남)
- GitHub의 PR 페이지에 "Delete branch" 버튼 있음
- 로컬에선 `git branch -d <이름>`

git은 **외울 게 적은데도** 처음엔 다 어려워 보입니다. 이유는 추상적인 단어가 많기 때문. 그래서:

1. 비유로 한 번 이해
2. 직접 한두 번 해봄
3. 까먹으면 이 매뉴얼 다시 봄

이 사이클이면 한 달 안에 익숙해집니다. 모르는 게 생기면 Claude에게:

> "지금 git 상태 보여줘"
> "지금 뭘 하려는 건지 모르겠는데 안전한 방법 알려줘"

라고 물어보면 됩니다. 잘못 누르기 전에 묻는 습관이 가장 안전합니다.
